## 1. The problem the harness has to solve

Physical-Engineering's Last Exam is not a question-answering benchmark with
engineering flavour. Each task hands the agent a real project folder — a
specification package, drawing sheets, soil borings, a spreadsheet template, a
cost workbook — and asks for a graded deliverable: a calculation package, a
review memo, an IFC model, a priced bill of materials, a witness-test schedule.
The deliverable is graded against constraints, and on the paper-score tasks a
single violated hard constraint (safety or feasibility) caps the item at 0.4 no
matter how good the rest is.

Two properties of the task set shape every design choice in this entry.

**The work is application-shaped, not text-shaped.** Filling a workbook means
opening the workbook; revising a drawing means editing the drawing's model;
answering a plan-check comment means producing a document in the reviewer's
format. A shell-only agent can read these files but cannot operate them, so it
either hand-writes binary formats from scratch — slow and error-prone — or
skips the application entirely and loses the deliverable.

**The clock runs.** Each task has a six-hour limit and a model call can take
minutes. A harness that plans forever, or that spends its budget on a single
tool call, ends with an empty deliverable and scores zero. Time has to be
allocated before the task starts, not discovered at the end.

## 2. Architecture (rubric: method; **Figure 1**)

```
                 ┌────────────────────────── serve.py ──────────────────────────┐
 task prompt ───►│ 1 discover   mcp_servers → initialize → tools/list           │
                 │                 each remote tool ⇒ mcp__<server>__<tool>      │
                 │ 2 plan       planner (bash, read_file, read-only MCP)        │
                 │ 3 work       worker (bash, files, **every MCP tool**)        │
                 │ 4 verify     fresh-context verifier → PASS | numbered gaps   │
                 │ 5 fix        ≤2 rounds, while the task clock allows          │
                 └───────┬───────────────────────────────┬──────────────────────┘
                         │ JSON-RPC over the evaluator    │ egress proxy
                         ▼                                ▼
              task container (no network)        google-cloud/<model>
```

The entry builds on the official `plan-verify` starter and adds one structural
change: **MCP discovery**. Starter harnesses ship `bash`, `read_file` and
`write_file` only, so `kit check` raises its `mcp` warning: the agent never
opens the applications a task serves.

At task start the harness reads the task's `mcp_servers` list, opens one
Streamable-HTTP JSON-RPC client per server through `taskbridge.MCPClient`, sends
`initialize` and `tools/list`, and synthesises an OpenAI function definition for
every remote tool from the server's own JSON Schema, named
`mcp__<server>__<tool>` and sanitised to `[A-Za-z0-9_-]`; the original name is
kept for the call, so `sheet.read` becomes `mcp__apps__sheet_read` and routes
back unchanged. The catalogue caps at 48 tools and 900 characters per
description, so a large application cannot crowd out the context. A discovery failure is logged and the run
continues with the shell tools rather than aborting the task.

Roles never share context. The planner explores the project and writes a
deliverable-by-deliverable plan (paths, formats, method, checks). The worker
executes it with every tool. The verifier starts from the task, the plan, and
the worker's summary only — deliberately without the worker's reasoning — and
re-opens each deliverable; it replies either `PASS` or a numbered list of gaps,
which go back to the worker for at most two fix rounds.

**Read-only MCP for the checking roles.** The verifier must inspect what the
worker produced, and for spreadsheet or CAD deliverables a shell cannot do that
well. But a verifier that can write is a verifier that can silently repair its
own findings. The planner and verifier therefore receive only the MCP tools
whose names read like readers (`get`, `list`, `read`, `search`, `query`,
`inspect`, `check`, …) and not like writers (`write`, `create`, `update`,
`delete`, `send`, `run`, …). The heuristic is name-based because MCP schemas do
not declare side effects; it is documented here as a heuristic, and
`test_mcp_tools.py` pins the behaviour on a stub server.

**Time budget.** The planner wraps up when 10% of the task clock is spent, the
worker when 25% remains, and verification and fix rounds use the remainder, with
a four-minute wrap-up per step. A step only starts if at least two minutes
remain before its own deadline, so the harness never begins a tool-less turn it
cannot finish.

## 4. Analysis: what the two changes buy (rubric: insight)

**No controlled ablation yet.** The honest position first: we have not run
`plan-verify` against `plan-verify-mcp` on the same tasks and model, so this
section reports what the dev run does show and what it cannot. The one
intervention we did measure is the spend cap, and it changed the trajectory of
the run in a way worth stating.

| observation | evidence | what it supports |
|---|---|---|
| Spend and score anti-correlate on this sample | cheapest task 38.9M tokens → 1.000; two most expensive 132M and 153M → 0.000 | the worker loop needed a bound, not a bigger budget |
| The bounded loop still finishes | after `PLE_MAX_STEPS`/`PLE_TOKEN_BUDGET` and an absolute deadline, a task stops on the same wrap-up path the clock uses, so it still writes its deliverable | capping cost does not mean cutting the run off mid-file |
| Twelve tasks never started | 0 s, 0 tokens, `evaluator: RuntimeError` | the dev pipeline must be batched, not one 17-task job |

Two claims we do **not** make, having no measurement for them: that the MCP
tools raise scores (no tool-free arm exists), and that the verifier pays for
its tokens. Both are the first experiment once batching is stable.

What the run supports is the design argument in §2: with application access the
worker wrote a workbook, a PDF and a memo rather than a description of them —
`landscape-sheet-revision` and `fire-test-validation-memo` are graded on files,
not prose, and both cleared 0.5.

## 5. Limitations (rubric: reflection)

- **Cost.** 458.9M tokens over five tasks, 91.8M on average and 152.7M at the
  worst: every tool round resent a growing history and nothing bounded the
  rounds. The caps in `serve.py` (`PLE_MAX_STEPS`, `PLE_TOKEN_BUDGET`, an
  absolute deadline, a 12k-character tool window) bound a task at roughly a
  tenth of that. They landed after this run, so §3 predates them; the same
  tasks under the cap are the ablation we owe.
- **Judge variance.** Rubric and `checks-judge` tasks are scored by an LLM
  judge. The dev scores above were produced with the judge pointed at the same
  local model the harness used (`JUDGE_MODEL=deepseek-chat`) rather than the
  official `google-cloud/claude-opus-5-5`; the organizer's rerun uses the
  official judge, so a rubric-heavy task can move between our number and theirs.
  Tasks graded by a checks script, which is most of the five above, are not
  affected.
- **No task branching.** The harness never reads graders, reference files, or
  `artifacts/`, and never branches on task identity. All adaptation happens
  through the plan and the verifier's feedback.
- **MCP read/write heuristic.** Name-based classification can mislabel a tool;
  a mislabelled writer would only reach the non-writing roles, and the worker
  keeps the full catalogue either way.
- **Heavy task images.** Twelve of the 29 dev tasks ship an image that installs a
  full engineering workstation (FreeCAD, LibreOffice, PostgreSQL, MySQL, nginx,
  PHP); the PLE docs put those images at about 17 GB in total. A free CI runner
  builds the seventeen light images comfortably but is not a reliable place to
  build the heavy ones, so the dev artifacts here cover the light tasks and the
  heavy ones report 0 in the average. A local Docker host or a larger runner
  removes that limitation without any change to the harness.
- **Next.** A deterministic unit-and-dimension checker (SI base units, load
  combinations, code-clause references) that runs between work and verify, and
  a cost-aware planner that assigns a token budget per deliverable.

## 6. Reproduction (rubric: reproducibility)

```bash
uv tool install harbor==0.20.0 --with websockets
export HF_TOKEN=…            # gated dev set, terms accepted
uv run python -m kit check ../harness
uv run python eval/run.py ../harness      # writes artifacts/ + runs/
```

`.github/workflows/dev-run.yml` runs the same two commands on a GitHub-hosted
Ubuntu runner. That is how the artifacts in this repository were produced: the
development machine had no Docker installation, so the kit and the dev set run
in CI instead. The workflow reproduces the two commands a local run would use,
plus three environment fixes the runner needs: it deletes preinstalled
toolchains to free disk, adds an 8 GiB swap file, and passes the model key
through repository secrets so the entry itself never contains one.

`PLE_TASK_BUDGET_SEC` caps the wall clock the harness spends inside a single
task. Unset, the harness uses whatever the task allows; set, the planner,
worker, verifier and fix rounds are budgeted inside the smaller window. That is
what lets one CI job cover many dev tasks without hitting the job timeout, and
it is the same code path — only the denominator of the time shares changes.

`artifacts/` is exactly that run's output; it is not edited by hand, and the
harness never reads it. `scripts/fetch_artifacts.py` downloads the run's
artifact archive and unpacks it into `artifacts/` so the commit matches the
workflow's output byte for byte.
